# App `billing`

**State:** billing plans: API + Admin (spec 024 in `features/history.md`); the screen is phase 4 part 06. Billing documents: API + Admin (spec 025). The monthly issuance: service, Celery tasks and `BillingRun` (spec 026). The draft boleto PDF: spec 027 (the phase 4 screen is part 06). Depends on `condominiums`, `persons`, `finance` and `core`.

## Rules worth knowing (the fields are in `models/`; the error codes in `errors/`)
- **`BillingPlan`** (the PDF's *PlanoCobranca*): a named plan of a condominium (unique name per condominium), `active`, optional `start_month` / `end_month` (first day of a month; the end not before the start). Its `condominium` never changes after creation. `BillingPlan.objects.in_force(reference_month)` is the active plans whose months include the reference month; the monthly issuance joins the items of all of them into **one** boleto per unit.
- **`BillingPlanItem`** (*ItemPlanoCobranca*): `description`, `cost_center` and `entry_template` (both active; the cost center of the plan's condominium, the template of that cost center; `PROTECT`), `calculation_kind` and only that kind's fields: `fixed_amount` → `amount` per unit; `ideal_fraction_share` → `amount` is the condominium's total, split by `ideal_fraction_number` (1 is `Unit.ideal_fraction`, 2–6 are `ideal_fraction_2` … `_6`); `unit_registered_value` → `unit_value_field` (`gas`, `water`, `electricity`: the unit's own value), no amount. Each kind rule is in `BillingPlanItemRules` and a check constraint. `position` is the order on the boleto. A share item may name a fraction no unit has yet: the issuance checks it.
- Shares are computed by the item (`BillingPlanItem.amounts_by_unit`): the total times the unit's fraction, rounded half-up to the cent, the leftover cents to the unit with the largest fraction (then by name), so the shares of all active units add up to the total. `uses_inconsistent_apportionment(totals)` says whether the named fraction does not close at 1 (a fraction no unit has counts).
- **`BillingDocument`** (*DocumentoCobranca*): a unit's boleto as a record. `unit` and `payer` (a `Person` of the same company) are `PROTECT`; `reference_month` and `competence_month` are on day 1; `status` is `issued` → `registered` → `paid`, or `cancelled` (`BillingDocument.ALLOWED_NEXT_STATUSES`; paid and cancelled are final). **Overdue is derived, never stored**: `is_overdue_on(date)` and `objects.overdue_on(date)` (still awaiting payment and due before the date). A unit has at most one non-cancelled document per `reference_month` (partial unique constraint), so a cancelled one can be issued again. The late-payment and discount terms (`discount_*`, `late_fee_percentage`, `initial_late_fee_*`, `interest_*`, `monthly_interest_percentage`) are copied from `BillingRules` and from the `LateInterestRate` in force on the due date when it is issued, so changing the rules later does not alter it. Everything but the status is frozen after issuance, and the amount equals the sum of the items (`BillingDocumentRules`). The bank or gateway fields are not here (phase 5).
- **`BillingDocumentItem`** (*DocumentoCobrancaItem*): `position`, `description`, `cost_center` (of the unit's condominium) and `entry_template` (of that cost center; the entry the payment will post), both `PROTECT`, positive `amount`. Active cost center and template are required only when the item is created; a saved item never changes.

## API (`/api/`)
`billing-plans`, company-scoped: list (`?condominium=`, `?active=`, `?query=` on the name), create, retrieve, update, delete (its items go with it). A plan is written **with its `items`** (at least one), all or none (`services/create_billing_plan.py`, `update_billing_plan.py`, `replace_billing_plan_items.py`): sending `items` replaces the whole list in the given order; a PATCH without `items` keeps them. An item error is reported as `items.<n>.<field>`: the nested serializer runs the item rules without the plan, then `BillingPlanSerializer` runs them again with the plan candidate attached (the cost center's condominium). Responses carry `condominium_name` and, per item, `cost_center_name` and `entry_template_name`. Both models are audited; the Admin shows a plan with its items inline.

`billing-documents`, company-scoped and **read only**: list (`?condominium=`, `?unit=`, `?payer=`, `?status=`, `?reference_month=`, `?competence_month=`, `?is_overdue=`, `?query=` on unit and payer name) and retrieve (with `items`, names of condominium, unit and payer, and `is_overdue`), plus `POST /{id}/cancel/` (an issued or registered document; anything else is a 400 `billing_document.status.transition_not_allowed`). Documents are created only by `services/create_billing_document.py` (`NewBillingDocument`: the amount is the sum of the items, the terms are copied, all or none; the condominium must have billing rules, which the monthly issuance checks first) and cancelled by `services/cancel_billing_document.py`. Both models are audited; the Admin is read-only, with the items inline.

## Monthly issuance (spec 026)
`services/issue_condominium_billing.py` issues a condominium's reference month and records a **`BillingRun`** (condominium, `reference_month`, `status` `running` / `succeeded` / `partial` / `failed`, `issued_count`, `already_issued_count`, `skipped_count`, `failed_count`, `started_at`, `finished_at`, and `problems`: a list of `{unit, code}` with `unit` null for a whole-condominium problem). It uses the items of every plan in force (`BillingPlan.objects.in_force`), in plan and position order, and `BillingRules` for the due date (`due_date_of`), the competence month and the terms.
- **Billed units:** active, not `is_billing_blocked`, and not the manager unit when `BillingRules.exempts_manager_unit`. A line of zero is omitted; a unit left with no line is skipped (`nothing_to_bill`). The payer is `Unit.billing_payer(today)`: the current tenant when `Unit.billing_recipient` is `tenant` and there is one, else the current owner with the largest share (the earliest link on a tie); none means `no_current_payer`.
- **Isolation and idempotency:** each unit is issued in its own transaction (`create_billing_document`); a document the model refuses is `failed` (`document_invalid`) and the run is `partial`. A unit that already has a non-cancelled document for the month is counted in `already_issued_count`, so a rerun adds nothing. `no_billing_rules`, `no_plan_in_force` and `inconsistent_apportionment` fail the whole run (`failed`) with nothing issued.
- **Problems in the API:** each entry of `problems` is answered as `{unit, unit_name, code}`; `unit_name` is the unit's block and number (one query per run) and is null for a whole-condominium problem; the stored JSON stays `{unit, code}`. The Cobrança screens (specs 028–029) turn the codes into Portuguese sentences and links.
- **Triggers:** `tasks.issue_due_billing` (beat, daily at 06:00 `TIME_ZONE`) enqueues `tasks.issue_condominium_billing_task` for each active condominium whose `BillingRules.issuance_day` is today, with the current month as the reference month. `POST /api/billing-runs/` {`condominium`, `reference_month` on day 1} runs the same service synchronously and answers the run; `GET /api/billing-runs/` (`?condominium=`, `?reference_month=`, `?status=`) and `GET /api/billing-runs/{id}/` read it. Runs cannot be edited or deleted; the Admin is read-only and the model is audited.

## Draft boleto PDF (spec 027)
**`BillingDocumentPdf`** is the current draft PDF of a document (one per document; the file lives in the bucket, `file_key` is built from the company id, document id and a random id). `services/render_billing_document_pdf.py` renders `templates/billing/boleto_draft.html` with WeasyPrint, whose `url_fetcher` refuses every URL, so rendering never touches the network or the file system; `boleto_template.py` shapes what the page prints (Brazilian money, CPF/CNPJ and date formats, the discount/fine/interest sentences taken from the terms copied onto the document). The page is Portuguese, carries the "RASCUNHO" watermark and "Sem valor para pagamento", and has no barcode or digitable line (a box says they appear once the title is registered); the administrator is shown by name (no logo yet, `known-gaps.md`).
- **Generation:** `services/generate_billing_document_pdf.py` renders, uploads with `ObjectStorage.put_object` and saves or replaces the row; the replaced file is deleted after the commit (a failed delete leaves an orphan). The issuance enqueues `tasks.generate_billing_document_pdf_task` (by name, `transaction.on_commit`; retries with backoff) for each document it creates; a PDF failure never undoes or blocks an issuance.
- **API:** `GET /api/billing-documents/{id}/pdf/` answers `{download_url, expires_in, generated_at}` (a signed URL valid 300 s) or a 404 `billing_document_pdf.not_generated`; `POST` generates or replaces it now (201 the first time, 200 after). An unconfigured bucket is the usual 503. Needs Pango and `fonts-liberation` (`architecture/operations.md`).
