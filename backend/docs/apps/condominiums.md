# App `condominiums`

The core registry: a condominium with its address, administration contract, billing rules, blocks, units and who owns or rents each unit. Depends on `core` and `persons`. Fields and constraints are in `models/`; `on_delete` and formulas in `architecture/data.md`.

## Rules worth knowing
- **`Condominium`**: `company` is the user's (read-only in the API); the `advisor` (a `Person`) must belong to the same company.
- **`code`** is the "ID" of a `Condominium`: a number from its own sequence (`condominium_code_seq`), unique, never reused and read-only; a term of only digits in `?query=` finds it first (spec 019). A `Unit` has no ID: it is its condominium plus its number (`name`, and the block when there is one). `Unit.registration_number` is another thing: the registry-office "matrícula", free text.
- **`AdministrationContract`** (1:1): the fee rules (fixed needs an amount, variable needs percentage and basis, floor ≤ ceiling) are `AdministrationContractRules`, each also guarded by a check constraint. `fee_floor` / `fee_ceiling` exist in the API but no screen uses them yet.
- **`BillingRules`** (1:1): `due_day` 1–28, discount 0–100, and (spec 020) the per-condominium late-payment rules. For a **reference month** (the month an issuance refers to), `due_month` (`reference` | `following`) says where the due date falls and `competence_month` (`same_as_due` | `before_due`) which month the boleto accounts for (`due_month_of`, `competence_month_of`; the old `calculation_period` is `due_month`, same database column). The fine is `late_fee_percentage`, at most 2 % (Civil Code art. 1.336 §1), and an optional first-days tier (`initial_late_fee_percentage` and `initial_late_fee_days`, both or neither: `BillingRulesRules`). The interest is counted as `full_month` or `per_day` (`interest_calculation`) after `interest_grace_days`; `should_show_qr_code` and `should_show_fee_statement` are boleto options. Nothing reads them yet: phases 4 and 5 will.
- **`LateInterestRate`**: the monthly interest of a condominium from a start date, one per `(condominium, start_date)`; `condominium.late_interest_rates.in_force_on(date)` is the rate with the latest start not after `date`, `None` before the first (no interest). A condominium with no rate charges no interest.
- **`Unit`**: its `block` must belong to the same condominium (`RESTRICT` on delete). It has up to **six ideal fractions**: `ideal_fraction` (the 1st) and `ideal_fraction_2` … `ideal_fraction_6` (`Unit.IDEAL_FRACTION_FIELDS`). For each fraction the active units of a condominium cannot sum more than 1 (`UnitRules`, one rule per fraction, all with the code `unit.ideal_fraction.sum_exceeds_total` on that fraction's field); reaching exactly 1 is only a dashboard pendency. A fraction is *in use* when some active unit has it; the 1st must always close at 1, the others only once in use (`Unit.is_apportionment_inconsistent`).
- **`UnitPerson`** (owner/tenant link): `UnitPersonRules` (an owner needs a percentage and a tenant has none; end not before start; the person belongs to the unit's company and to the `condominiums` module, checked when the link is created or its person changes, so a person who later leaves the module keeps the links they have; owners sum at most 100% at any date). One active link per `(unit, person, role)`.
- Reusable queries live in `models/querysets/` (`UnitPerson.objects.current` / `leases_ending_soon`, `Unit.objects.without_responsible` / `with_lease_ending_soon`, `Condominium.objects.without_cost_centers`, the adjustment queries of the contract). The dashboard and the `?pending=` filters call the same ones, so their numbers match. Block CRUD has an API but no screen.

## API (`/api/`)
`condominiums`, `blocks`, `units`, `unit-people`, `late-interest-rates`, all company-scoped (another company's id is 404; as a related id, 400 `does_not_exist`). Filters and search: see the viewsets and the OpenAPI schema. `GET /api/condominiums/{id}/apportionment/` answers the active units and, for each of the six fractions, its total and whether it is inconsistent (a condominium with no active unit flags nothing); the list and detail payloads do not carry it. `?pending=` on `condominiums` (`without_cost_centers`, `inconsistent_apportionment`, `overdue_adjustment`, `upcoming_adjustment`) and on `units` (`without_responsible`, `lease_ending`, `billing_blocked`); any other value is a 400.

`CondominiumSerializer` validates the nested `address`, `administration_contract` and `billing_rules` and calls the `create_condominium` / `update_condominium` services (`services/`), which write them atomically: the address is created or updated in place (it cannot be cleared), the contract and rules use `update_or_create`. Every serializer inherits `ModelRulesMixin`, so a violation is a 400 with the model's message and code.
