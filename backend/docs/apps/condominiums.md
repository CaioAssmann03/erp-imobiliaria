# App `condominiums`

The core registry: a condominium with its address, administration contract, blocks, units and who owns or rents each unit. Depends on `core` and `persons`. Fields and constraints are in `models/`; `on_delete` and formulas in `architecture/data.md`.

## Rules worth knowing
- **`Condominium`**: `company` is the user's (read-only in the API); the `advisor` (a `Person`) must belong to the same company.
- **`code`** is the "ID" of a `Condominium`: a number from its own sequence (`condominium_code_seq`), unique, never reused and read-only; a term of only digits in `?query=` finds it first (spec 019). A `Unit` has no ID: it is its condominium plus its number (`name`, and the block when there is one). `Unit.registration_number` is another thing: the registry-office "matrícula", free text.
- **`CondominiumAdministrationContract`** (1:1; `is_due_in(month)`, `fee_before_limits(base)` and `fee_for(base)` are the fee arithmetic the administration fee report uses, spec 056): the fee rules (fixed needs an amount, variable needs percentage and basis, floor ≤ ceiling) are `CondominiumAdministrationContractRules`, each also guarded by a check constraint. `fee_floor` / `fee_ceiling` exist in the API but no screen uses them yet.
- **Billing rules and late interest rates** are not here: they moved to `billing` (spec 041; `CondominiumBillingRules` and `LateInterestRate`, see `apps/billing.md`). `condominiums` imports nothing from `billing`; `condominium.billing_rules` and `condominium.late_interest_rates` exist as reverse relations only while `billing` is installed.
- **`CondominiumApportionmentCriterion`** (spec 047): one way a condominium splits its expenses, with the name the condominium gives it ("Geral", "Elevador"). `name` is unique per condominium and `position` is the next free one at creation (it is read-only in the API; reordering does not exist yet). The criterion at position 1 is the **main** one: `Condominium.save()` creates it ("Geral") with every new condominium, it cannot be deleted, and it always has to close at 1. Any criterion is refused deletion (`CondominiumApportionmentCriterion.delete()`, a coded 400) while a unit fraction or a billing plan item uses it; its condominium cannot change. There is no maximum.
- **`UnitApportionmentFraction`**: a unit's share (0 < value ≤ 1, `Decimal(9, 8)`) in one criterion; unique per `(unit, criterion)`; the criterion must belong to the unit's condominium. For each criterion the active units of a condominium cannot sum more than 1 (`UnitApportionmentFractionRules`, code `unit.ideal_fraction.sum_exceeds_total` on `value`; an inactive unit does not count, and reactivating one re-checks its fractions in `UnitRules`); reaching exactly 1 is only a dashboard pendency. A criterion is *in use* when some active unit has a fraction in it: the main one must always close at 1, the others only once in use (`CondominiumApportionmentCriterion.is_inconsistent`, with the constants `TOTAL` and `TOLERANCE`). `ApportionmentCriterionQuerySet` does the sums in the database: `with_total()` (the fractions' sum over the active units, optionally of a given unit queryset), `main()` and `inconsistent()` (the pendency); the dashboard, `?pending=` and the totals endpoint all read it. A unit's set is written by the `set_unit_fractions` service (through `create_unit` / `update_unit`): all rows in one transaction with the condominium's units locked, each validated by the model rules only after all are written.
- **`Unit`**: its `block` must belong to the same condominium (`RESTRICT` on delete). `billing_recipient` (`owner` default / `tenant`) says who receives its boleto and `billing_payer(reference_date)` picks that person: the current tenant when it is `tenant` and there is one, else the current owner with the largest `ownership_percentage` (the earliest link on a tie), or none. Its shares in the condominium's apportionment are **`UnitApportionmentFraction`** rows (below).
- **`UnitPerson`** (owner/tenant link): `UnitPersonRules` (an owner needs a percentage and a tenant has none; end not before start; the person belongs to the unit's company and has a `PersonModuleMembership` for the `condominiums` module (spec 048), checked when the link is created or its person changes, so a person who later leaves the module keeps the links they have; owners sum at most 100% at any date). One active link per `(unit, person, role)`.
- Reusable queries live in `models/querysets/` (`UnitPerson.objects.current` / `leases_ending_soon`, `Unit.objects.without_responsible` / `with_lease_ending_soon`, `Condominium.objects.without_cost_centers`, the adjustment queries of the contract). The dashboard and the `?pending=` filters call the same ones, so their numbers match. Block CRUD has an API but no screen.

## API (`/api/`)
`condominiums`, `blocks`, `units`, `unit-people`, `condominium-apportionment-criteria` (`?condominium=`; create takes `condominium` and `name`, rename is a PATCH), all company-scoped (another company's id is 404; as a related id, 400 `does_not_exist`). Filters and search: see the viewsets and the OpenAPI schema. `GET /api/condominiums/{id}/apportionment/` answers the active units and, for each criterion of the condominium (`criteria[]`: `criterion`, `name`, `position`, `total`, `is_inconsistent`), its total and whether it is inconsistent (a condominium with no active unit flags nothing); the list and detail payloads do not carry it. A unit's payload carries `fractions: [{criterion, value}]`: sending the list replaces the unit's whole set (an empty list clears it), leaving it out keeps it; a refusal comes back on `fractions`. `?pending=` on `condominiums` (`without_cost_centers`, `inconsistent_apportionment`, `overdue_adjustment`, `upcoming_adjustment`) and on `units` (`without_responsible`, `lease_ending`, `billing_blocked`); any other value is a 400.

`CondominiumSerializer` validates the nested `address` and `administration_contract` and calls the `create_condominium` / `update_condominium` services (`services/`), which write them atomically: the address (`core.Address`, spec 043) is created under the company or updated in place (it cannot be cleared), the contract uses `update_or_create`. Every serializer inherits `ModelRulesMixin`, so a violation is a 400 with the model's message and code.
